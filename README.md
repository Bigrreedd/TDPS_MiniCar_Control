# UESTCHN3018 TDPS 微缩车模控制程序

本仓库用于 UESTCHN3018 Team Design Project and Skills 课程的微缩车模（Patio 赛道）底层 C 语言控制程序的团队协同开发。
仓库地址：https://github.com/Bigrreedd/TDPS_MiniCar_Control.git

为了保证 5 人团队的高效协作与代码安全，请所有成员严格遵守本指南中的 **VS Code + Git** 工作流操作规范。

---

## 一、 环境准备

1. **安装 Git**：确保电脑已安装 Git 客户端。
2. **安装 VS Code**：推荐作为代码编辑和 Git 版本控制的主力工具。
3. **安装 Keil MDK**：用于工程编译、烧录与调试。

---

## 二、 初次获取代码（Clone）

*此操作每台电脑仅需执行一次。*

1. 打开 VS Code。
2. 按 `Ctrl + Shift + P` (Windows) 或 `Cmd + Shift + P` (Mac) 调出命令面板。
3. 输入并选择 `Git: Clone` (克隆)。
4. 粘贴本仓库地址：`https://github.com/Bigrreedd/TDPS_MiniCar_Control.git`
5. 选择一个**不包含中文路径**的本地文件夹存放代码（避免 Keil 编译报错）。
6. 克隆完成后，在 VS Code 中点击“打开”。

---

## 三、 日常协作核心工作流 (The Core Workflow)

每次开始写代码，或写完准备分享给队友时，**必须严格按以下顺序操作**：

### 1. 编写前必做：拉取 (Pull)
* **目的**：获取队友的最新代码，预防冲突。
* **操作**：点击左侧边栏第三个图标 **源代码管理 (Source Control)** -> 点击面板右上角的 `...` -> 选择 **拉取 (Pull)**。

### 2. 编写代码 (Modify)
* 在 Keil 或 VS Code 中正常修改 `.c` 或 `.h` 文件。
* **注意**：修改完成后务必按 `Ctrl + S` 保存文件，VS Code 才能检测到更改。

### 3. 暂存与提交 (Stage & Commit)
* **操作**：
  1. 在 VS Code 的 **源代码管理** 面板中，检查 **更改 (Changes)** 列表。
  2. 点击你要上传的文件右侧的 **`+` 号 (暂存更改)**。
  3. 在顶部的消息框中输入**规范的提交说明**。
  4. 点击 **提交 (Commit)**。
* **提交说明规范**：`<动作>: <修改的具体模块及原因>`
  * *正确示例*：`Update BlackPoint_Finder.c: 优化起步线搜索逻辑`
  * *错误示例*：`改代码`、`123`、`update`

### 4. 推送到云端 (Push)
* **操作**：点击 **源代码管理** 面板中的蓝色按钮 **同步更改 (Sync Changes)**。
* **结果**：你的代码正式上传到 GitHub，队友可以拉取到了。

## 四、 团队分支与防冲突策略

5 人同时修改同一个工程极易产生冲突。请遵守以下原则：

### 1. 功能隔离（使用分支）
开发独立大功能（如 LoRa 通信、雷达扫描等）时，不要在 `main` 主干上直接修改。
1. **创建分支**：点击 VS Code 左下角的 `main` -> 选择 **创建新分支** -> 命名（例：`ZJ/feature-radar`）。
2. **发布分支**：点击旁边的云朵图标将分支发布到 GitHub。
3. **合并主干**：功能开发完毕并测试通过后，切换回 `main` 分支，在命令面板 (`Ctrl+Shift+P`) 输入 `Git: Merge Branch`，选择你的开发分支进行合并，最后 Push 到云端。

### 2. 解决合并冲突 (Merge Conflict)
如果 Push 或 Pull 时提示冲突，代码中会出现如下标记：

```c
<<<<<<< HEAD (当前更改)
float i_speed = 250;  // 你的代码
=======
float i_speed = 280;  // 队友的代码
>>>>>>> [hash值] (传入的更改)
```

* **解决办法**：VS Code 会在上方提供绿色快捷按钮（`保留当前更改` / `保留传入的更改` / `保留双方更改`）。点击正确的选项，按 `Ctrl+S` 保存，然后重新点击 `+` 暂存并 **Commit** 即可。

## 五、 ⚠️ Keil 工程特有协作红线

Keil 工程在编译时会产生大量垃圾文件，处理不当会直接导致团队代码库崩溃。

1. **绝对禁止上传中间文件**：只上传代码和工程配置文件。本仓库已配置 `.gitignore`，请确保生效（`Objects/` 和 `Listings/` 文件夹不应出现在 VS Code 的更改列表中）。
2. **正确提交 `.uvprojx`**：如果你在 Keil 的 Project Tree 中**新建或移除了 `.c/.h` 文件**，Keil 会自动修改根目录下的 `Project.uvprojx` 文件。**你必须将该 `.uvprojx` 文件与新建的代码文件一起暂存并提交**，否则队友拉取后工程中会缺少该文件。
3. **绝对禁止提交 `.uvoptx`**：该文件包含了你个人的窗口布局、J-Link 调试配置等本地信息，提交会导致队友的调试配置被覆盖。
